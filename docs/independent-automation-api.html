เขียน REST API และ MCP ของเราเอง
ให้ทีมใช้ร่วมกันได้จริงแค่ไหน?

ทำได้ โดยเขียนตัวบริการและตัวควบคุมอุปกรณ์เอง ใช้ความสามารถของ Appium, Maestro, Playwright และ Mobilewright เป็นข้อกำหนดอ้างอิง ไม่ใช่ fork หรือเรียก MCP/automation engine ของเขาอยู่ข้างหลัง

ขอบเขต: ใช้ภายในองค์กรหลายคน อาจมีหน้าเว็บ public URL ที่แชร์เฉพาะทีม แต่การเปิดหน้าเว็บกับการเปิดสิทธิ์ควบคุมเครื่องทดสอบเป็นคนละเรื่อง

ข้อสรุปต้องสร้างอะไรทางเลือก runnerความสามารถREST → MCPข้อจำกัดความพร้อมใช้งานแหล่งข้อมูล

ข้อสรุปก่อน

สร้างเครื่องมือที่ทีมใช้ทำงานประจำได้จริง: เป็นไปได้
แต่การเขียน REST routes และ MCP tools ไม่ได้ทำให้ควบคุมอุปกรณ์ได้เอง งานใหญ่คือตัว runner, การหา element, การรอ UI, การกู้ session และการทดสอบกับ OS/อุปกรณ์จริง
  • เหมือนในเชิงความสามารถ: อ่านหน้าจอ หา element แตะ พิมพ์ ปัด เปิดแอป ทดสอบ flow และเก็บผล สามารถออกแบบให้เทียบเคียงกันได้ด้วย API ของแต่ละแพลตฟอร์ม [Apple] [Android] [Chrome]
  • ไม่เท่ากับรองรับทุกอย่าง 100%: การรันโค้ด Playwright เดิม, ตั้งค่า Appium driver เดิม หรือส่งงานเข้าบริการ Cloud ของผู้ให้บริการ เป็นสัญญาเฉพาะของระบบนั้น ต้องสร้างทางเลือกของเรา หรือยอมระบุว่าไม่รองรับ [รายการอ้างอิง]
  • 149 tools เป็นข้อมูลวิจัย: ไม่ใช่ 149 ความสามารถที่เราพัฒนาและทดสอบแล้ว และจำนวนชื่อ tools ไม่ใช่ตัววัดความเท่าเทียม

สถานะรายงาน: ตรวจ source/documentation และประเมินทางวิศวกรรม ยังไม่ได้สร้างหรือทดสอบ native runner ในรอบนี้ ข้อเสนอด้านสถาปัตยกรรม ระดับความยาก และระยะเวลาไม่ใช่ผล benchmark

สิ่งที่ต้องสร้างเอง

REST API และ MCP ในข้อเสนอนี้เป็นขององค์กรเราเอง ส่วนชั้น runner เลือกได้สองแนวทางด้านล่าง การใช้ library/driver ใต้ API ของเราไม่ใช่การ fork หรือการห่อ MCP ของผู้ให้บริการเดิม และ native runner ก็ไม่ใช่ข้อบังคับของโจทย์

1. MCP ของเราTypeScript + MCP SDK

ประกาศ tools, ตรวจ arguments, แปลงผล/ภาพ/error ให้ agent เรียกได้

เรียก REST API เดียวกับ UI/CI →
2. REST API ของเราTypeScript + HTTP framework + OpenAPI

session, capability registry, คิว, device lease, job timeout, logs และ artifacts

ส่งคำสั่งที่ตรวจสอบแล้ว →
3. Runner ของเรา
  1. iOS: Swift + XCTest/XCUIAutomation ใน UI-test runner และ host service บน Mac
  2. Android: Kotlin + AndroidX UI Automator ใน instrumentation APK และ host service ผ่าน ADB
  3. Web: ตัว client Chrome DevTools Protocol (CDP) ของเรา เริ่ม Chromium ก่อน

iOS runner

เขียน UI-test target ที่รับคำสั่งแบบมีขอบเขตและเรียก XCUIApplication/XCUIElement เอง ไม่ใช่แอป iOS ปกติที่ขอสิทธิ์แล้วควบคุมทุกแอปได้ ต้องสร้างการสื่อสาร host ↔ test runner, command loop, element references และการ restart หลัง runner ตายเอง [Apple] [XCTest]

Mac host ใช้ Xcode tools จัดการ build/test และ simulator/device lifecycle; อุปกรณ์จริงมี signing/provisioning และการเตรียมเครื่องเพิ่ม ไม่ได้ย้ายไปรันทั้งหมดใน Linux container แล้วจบ [Xcode tools] [real device]

Android และ browser runner

Android ใช้ instrumentation เพื่ออ่าน/โต้ตอบ UI และ ADB จัดการอุปกรณ์ แอป ไฟล์ และ logs ไม่พึ่งการส่ง adb shell input อย่างเดียว เพราะไม่แก้เรื่อง selectors และ synchronization [UI Automator] [ADB]

Browser ใช้ CDP ติดต่อ Chromium ผ่าน WebSocket ได้โดยตรง แต่ต้องเขียน locator semantics, auto-wait, frame handling และ event correlation เอง การรองรับ Firefox/Safari ต้องมี backend อื่น ไม่ได้ตามมาจาก CDP [CDP]

Dependency ที่ยังต้องมี: runtime/HTTP framework, MCP SDK, Swift/Xcode, Kotlin/Gradle/JDK/Android SDK, UI Automator, browser binary และ client WebSocket ส่วนฐานข้อมูล คิว และ object storage เลือกตามขนาดระบบได้ ไม่จำเป็นต้องเริ่มด้วย Kubernetes หรือ device farm ขนาดใหญ่

สองทางเลือกของชั้น runner

A. ใช้ library/driver ใต้ REST API ของเรา

เลือกใช้ automation library หรือ protocol client ที่มี license และขอบเขตเหมาะสม แล้ววาง session, auth, queue, capability registry, error model และ artifacts ไว้ใน service ของเราเอง ตัวอย่างเช่นใช้ Playwright library สำหรับ Chromium หรือใช้ client ที่พูดกับ driver ของแพลตฟอร์ม โดยไม่เปิด MCP เดิมเป็น backend

ข้อดี: ได้ locator, waits, browser contexts และ edge cases เร็วกว่า ลดโค้ด native ที่ต้องดูแลเอง

ข้อแลกเปลี่ยน: ต้องยอมรับ API/version/license ของ dependency และอาจไม่ได้ portability หรือ semantics แบบเดียวกันทุก platform; ต้องตรวจว่า driver ที่ใช้ยังทำให้ระบบเป็นเจ้าของ execution boundary จริง

B. เขียน native runner ของเราเอง

ใช้ XCTest/XCUIAutomation, Android UI Automator/ADB และ CDP เป็น system API/protocol แล้วสร้าง locator, waits, stale references, recovery และ lifecycle เองทั้งหมด

ข้อดี: ควบคุม contract, data flow และการผูกกับองค์กรได้ลึก ลดการผูกกับ framework ระดับสูง

ข้อแลกเปลี่ยน: ใช้เวลามากกว่าและต้องรับผิดชอบความเสถียร/compatibility เอง โดยเฉพาะ iOS signing, Android versions, browser protocol และการกู้ runner

ข้อเสนอเชิงปฏิบัติ: เริ่มจาก REST/MCP contract เดียวกัน แล้วทำ vertical slice ด้วย library/driver ที่ผ่านการตรวจ license และ security เพื่อพิสูจน์ workflow ก่อน จากนั้นค่อยแทนที่เฉพาะจุดด้วย native implementation เมื่อมีเหตุผลด้าน capability, reliability, cost หรือ data boundary ไม่ควรถือว่าการเขียน native ทั้งหมดเป็น acceptance criterion โดยอัตโนมัติ

ไม่ว่าทางเลือกใด สิ่งที่เป็นของเราและต้องทดสอบเองยังเหมือนกัน: multi-user session/lease, authorization, cancellation, cleanup, artifacts, observability, support matrix และ error semantics การใช้ dependency ไม่ได้ทำให้ความสามารถของ dependency กลายเป็นความสามารถที่ repo นี้มีอยู่แล้ว

ความสามารถที่จะทำให้ใกล้เคียงต้นแบบ

เป็นการประเมินแนวทางเขียนใหม่ ไม่ใช่สถานะ implementation: “ทำได้” หมายถึงมี primitive ให้พัฒนา ไม่ได้หมายความว่าทำเสร็จหรือเสถียรแล้ว ส่วนที่ต่างกันบางฟังก์ชันยังเก็บแยก ไม่ยุบด้วยชื่อที่คล้ายกัน

REST API ก่อน แล้วค่อยประกาศ MCP ของเรา

ตัวอย่างต่อไปนี้เป็น design proposal ไม่ใช่ endpoints ที่พร้อมเรียกใช้งาน ให้ business logic อยู่ใน service layer เดียว MCP เรียก REST API นี้ และ UI/CI ก็ใช้ API เดียวกัน ไม่สร้าง automation logic ซ้ำใน MCP

  • ใช้ capability registry กลางบอก support ราย action, platform, OS, runner version และข้อจำกัด รักษาความแตกต่าง เช่น element screenshot กับ full-page screenshot และ directional swipe กับ multi-touch
  • ทุกคำสั่งผูก sessionId และ device lease; references ผูก snapshot revision และแจ้ง stale เมื่อใช้ไม่ได้ ไม่คลิกพิกัดเดิมต่อเงียบ ๆ
  • ยอมรับงานยาวด้วย job ID แล้วให้ poll/events/cancel; กำหนด timeout, error codes และ artifact lifecycle ให้ชัด การกดปุ่มซ้ำไม่ควรถูก retry อัตโนมัติเมื่อไม่รู้ว่าครั้งแรกสำเร็จหรือไม่
  • MCP ใช้ SDK มาตรฐานได้โดยไม่พึ่ง MCP ของผู้ให้บริการเดิม สำหรับบริการส่วนกลางใช้ Streamable HTTP; stdio เป็นตัวเลือกแพ็กเกจที่รันใกล้ client ไม่ใช่ข้อบังคับว่าทุกคนต้องใช้เครื่องผู้พัฒนา [MCP transport]

ข้อจำกัดจากแพลตฟอร์ม

  • Runner สร้าง accessibility ID ที่แอปไม่ได้กำหนดไว้ให้เองไม่ได้ ต้องใช้ locator อื่นหรือแก้แอปให้ expose semantics [identifier]
  • Custom drawing, canvas, video และรายการที่ยังไม่ render อาจไม่มี tree ที่ใช้หา element ได้ ภาพ/OCR เป็น fallback แต่ไม่เท่ากับมี semantic IDs
  • iOS ต้องมี Mac runner และ test/signing lifecycle ของจริง; simulator กับเครื่องจริงต้องผ่าน acceptance แยก [Xcode] [device preparation]
  • OS updates และ browser protocol changes ทำให้พังได้ ต้อง pin/test versions; CDP tip-of-tree ไม่รับประกัน backwards compatibility [protocol versioning]

ข้อจำกัดจากการใช้ร่วมกัน

  • ทีม 10 คนใช้ device เดียวได้ด้วยคิว ไม่ใช่ควบคุมพร้อมกัน 10 sessions; เพิ่ม concurrency ด้วยหลายอุปกรณ์หรือแยก emulator/browser contexts ตามงาน
  • อุปกรณ์ test ต้องมี test accounts, cleanup และการคืน lease หลัง client หลุด ไม่ใช้เครื่อง/บัญชีส่วนตัวของคนในทีมเป็น shared target โดยปริยาย
  • หน้าเอกสาร/catalog ใช้ public URL ได้ แต่ “ไม่ประกาศ URL” ไม่ใช่ access control หาก endpoint ควบคุมอุปกรณ์เปิด public และไม่มี auth ผู้ที่เข้าถึง endpoint ได้ก็สามารถเรียกใช้ได้
  • ถ้าต้องการ no-auth ที่ application layer ให้จำกัด API ด้วย VPN/internal network/allowlist แทน; หน้าเว็บ public สามารถแสดงเอกสารโดยไม่เปิด execution API ตามไปด้วย ข้อนี้เป็นข้อเสนอการ deploy ไม่ใช่การตั้งค่าที่ทำแล้ว
License มีผลอย่างไรเมื่อเขียนใหม่?

การศึกษาความสามารถแล้วเขียน implementation เองต่างจากการคัดลอก source รายงานนี้ไม่กำหนดให้ใช้ MobileCLI/DeviceKit จึงไม่ต้องนำ FSL runtime มาประกอบระบบตามแบบนี้ MIT ของ repo ครอบคลุมงานที่เราเป็นเจ้าของ ไม่ได้เปลี่ยน license ของ SDK, binary หรือโค้ดที่อาจนำเข้าภายหลัง

ถ้าเปลี่ยนใจนำโค้ดเดิมมาใช้: Appium MCP, Maestro core, Playwright MCP และ Mobile MCP/Mobilewright มี Apache-2.0 แต่ Mobile Next MobileCLI/DeviceKit ใช้ FSL 1.1 ซึ่งระบุ internal use เป็น permitted purpose และมีเงื่อนไขเรื่อง competing commercial use ต้องตรวจ version/dependency chain และเก็บ notices ตาม license จริง ไม่ใช่ดู badge ของ wrapper อย่างเดียว [Apache] [MobileCLI license] [DeviceKit license] ทั้งนี้ไม่ใช่การรับรองทางกฎหมายหรือการตรวจสิทธิ์ dependency ทั้งระบบ

ทำให้ใช้งานได้จริงแค่ไหน

ข้อประเมิน: เหมาะกับการสร้างเครื่องมือภายในที่รองรับแพลตฟอร์ม/รุ่น/flows ที่ทีมกำหนดชัดเจน ไม่ควรเริ่มด้วยคำสัญญาว่าแทนทุก tool ของทั้งสี่ ecosystem ได้ 100%

  1. พิสูจน์ vertical slice บนแพลตฟอร์มแรก: จอง session → เปิดแอป → อ่าน tree → หา element → แตะ/พิมพ์ → assert → screenshot → คืนเครื่อง โดยเรียกได้ทั้ง REST และ MCP ถ้า loop นี้ยังไม่ผ่านบนอุปกรณ์จริง การเพิ่มชื่อ tools ยังไม่มีน้ำหนัก
  2. ทำ core ให้ทีมทดลองใช้: เพิ่มแพลตฟอร์มที่สอง/Chromium, waits, errors, run history, queue, logs และ artifacts ทดสอบผู้ใช้สองคนและการตัด connection อย่างตั้งใจ
  3. เติมความสามารถเฉพาะที่ทีมต้องใช้: WebView, network mocking, flow DSL, recorder, video และ viewer แยกเป็นงานจริง ไม่ซ่อนไว้ในชื่อ generic action เดียว
  4. พิจารณา near-parity ภายหลัง: รองรับหลาย browser/OS, advanced actions และ vendor-format compatibility ก็ต่อเมื่อมี contract tests และต้นทุนดูแลที่ทีมรับได้
การวางแผนคร่าว ๆ ไม่ใช่กำหนดส่ง: ถ้ามีผู้พัฒนา 2–3 คนที่ถนัด native/browser และมีเครื่องทดสอบพร้อม vertical slice หนึ่งแพลตฟอร์มอาจใช้ราว 2–4 สัปดาห์; ระบบ core หลายแพลตฟอร์มพร้อม pilot ภายในควรวางแผนเป็นหลายเดือน; ความใกล้เคียงกว้างทั้ง ecosystem อาจเป็นงาน 6–12 เดือนขึ้นไป ขอบเขตอุปกรณ์และ compatibility เปลี่ยนตัวเลขนี้ได้มาก ยังไม่มี spike หรือ benchmark ของเราเพื่อยืนยัน

เกณฑ์ก่อนเรียกว่า “พร้อมให้ทีมใช้” — ข้อเสนอ ยังไม่ผ่านการทดสอบ

  • กำหนด flows ตัวแทนบนแอปของทีม และรันซ้ำอย่างน้อย 20 ครั้งต่อ flow/target ที่รองรับ แสดง first-attempt pass rate แยกจาก pass-after-retry พร้อม latency และสาเหตุ fail ไม่ใช้จำนวน REST unit tests แทนผล device E2E
  • ทดสอบ missing/ambiguous element, stale ref, app crash, runner disconnect, deadline และ cancellation; ผลต้องเป็น error ที่อธิบายได้ ไม่ใช่ HTTP 200 พร้อม success จำลอง
  • พิสูจน์ว่าผู้ใช้สองคนแย่งเครื่องเดียวกันไม่ได้ และการปล่อย lease/cleanup ทำงานแม้ MCP client หลุด
  • ประกาศ support matrix ต่อ action/OS/device type; action ที่ทำไม่ได้ต้องระบุ unsupported จริง ไม่แทนด้วย action ที่ใกล้เคียงโดยไม่บอก
  • มีขั้นตอนติดตั้ง runner, signing/provisioning, upgrade/rollback และเก็บ artifacts ที่สมาชิกทีมคนอื่นทำตามได้

สถานะปัจจุบันของ repo: มีเว็บไซต์วิจัย/catalog และ logic เปรียบเทียบ tools และเริ่ม Chromium vertical slice ใน execution/ (REST + MCP stdio + Playwright library runner, acceptance tests ผ่านบน fixture HTML) ยังไม่มี iOS/Android runner, auth สำหรับเปิด public, หรือผล E2E บนแอปทีม จึงยังไม่สามารถอ้างเปอร์เซ็นต์ coverage หรือ reliability ของระบบเต็มได้
